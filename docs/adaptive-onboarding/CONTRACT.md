# Adaptive onboarding: build contract (14 Oct 2026)

Approved design: `/home/claude/107-adaptive-onboarding-tree-20261014.md` (Arabic; read sections 2 to 4 in full before writing rules or copy).
Shared types: `lib/setup/adaptive/types.ts`. Do not change a type's meaning; if you must add a field, add it as optional and say so in your report.

## Hard rules for every part
- **No model call anywhere.** Classification, questions, copy and decisions are rules and templates in code. Before a subscription the only AI spend allowed is the free audit, which already exists and is not touched.
- **No migration.** Answers are `business_memory` facts with `data.setup_key` (as today); signals live in `job_runs`.
- Do not touch Supabase, Vercel, secrets, or push. Commit on your own branch in your own worktree; the coordinator merges.
- Everything new is behind `isAdaptiveOnboarding()` (`lib/setup/adaptive/flag.ts`). With the flag off, `/onboarding` must behave exactly as on main.
- A signal that failed to read (`{ ok: false }`) never drives a branch. The tree falls back to asking.
- Run `pnpm typecheck`, `pnpm lint` and `pnpm test` before you report; all must pass.

## Arabic copy rules (every string a customer reads)
Saudi Najdi, short, the way the existing setup copy in `lib/setup/questions.ts` and `app/onboarding/setup/setup-chat.tsx` reads. Then:
- Never the long or medium dash (U+2014, U+2013) in Arabic text. Use «،» or a new sentence. Ranges are «من كذا إلى كذا».
- Never the Latin comma inside Arabic prose (digits like 3,200 are fine: that is the app's number format).
- No «ليس مجرد»، «بالإضافة إلى ذلك»، «علاوة على ذلك»، «من الجدير بالذكر»، «حلول متكاملة»، «رحلتك»، «باختصار».
- No invented numbers. Every number shown comes from the account or the customer's answer.
- No three balanced items in a row as a rhetorical pattern; vary sentence length.
- The assistant's name is «مُضاعِف» (from `lib/assistant/persona.ts`), never «زياد».

## Part A: signals
`readAccountSignals(customer, ctx)` runs one GAQL query per signal in parallel, each with its own try/catch, all inside one deadline (`SIGNALS_TIMEOUT_MS`). It never throws. Queries (verify field names against the Google Ads API v22 reference; a field Google rejects just makes that signal `{ ok:false }`):
- campaigns: `campaign.id, campaign.name, campaign.status, campaign.advertising_channel_type, metrics.cost_micros, metrics.impressions, metrics.clicks, metrics.conversions, metrics.conversions_value` FROM campaign, `segments.date DURING LAST_30_DAYS`, `campaign.status != 'REMOVED'`. A campaign with zero activity still has to appear: run a second metrics-free query for non-removed campaigns and merge (same idea as `lib/google-ads/sync.ts`). Map channel types like `normalizeChannel` there (PERFORMANCE_MAX to PMAX, MULTI_CHANNEL to APP, else OTHER).
- enabledConversionActions: same query as `lib/audit/live-snapshot.ts` (count of ENABLED actions).
- conversionsByGroup: `segments.conversion_action_category, metrics.conversions` FROM customer, LAST_30_DAYS. Fold Google's categories: PURCHASE, ADD_TO_CART, BEGIN_CHECKOUT, STORE_SALE to purchase; SUBMIT_LEAD_FORM, QUALIFIED_LEAD, CONVERTED_LEAD, IMPORTED_LEAD to lead_form; PHONE_CALL_LEAD to call; BOOK_APPOINTMENT, REQUEST_QUOTE to booking; GET_DIRECTIONS to directions; STORE_VISIT to store_visit; CONTACT to contact; SIGNUP, SUBSCRIBE_PAID to signup; PAGE_VIEW, ENGAGEMENT to page_view; anything else to other.
- autoTagging: `customer.auto_tagging_enabled`.
- landingHosts: `ad_group_ad.ad.final_urls` (enabled ads in enabled campaigns, LIMIT 200) and `asset_group.final_urls` (LIMIT 50); hostnames lowercased without `www.`, counted, top 10. Either query alone is enough for ok:true.
- merchantCenterLinked: `campaign.shopping_setting.merchant_id` on non-removed campaigns; true when any is non-zero.
- assets: `customer_asset.field_type` and `campaign_asset.field_type` (status ENABLED); call = any CALL; locations = count of LOCATION rows (and `asset_set` locations if cheap).
- targetedPlaces: `campaign_criterion.location.geo_target_constant` where `campaign_criterion.type = 'LOCATION'`, not negative, enabled campaigns; then names via `geo_target_constant.name` for those resource names (one IN query, at most 12).
- externalManager: `customer_manager_link.manager_customer, customer_manager_link.status` FROM customer_manager_link; linked = any ACTIVE whose id (digits) is not in `ctx.ownManagerIds`.
- otherEditors14d: change_event `DURING LAST_14_DAYS ... LIMIT 1000` with `change_event.user_email, change_event.client_type`; count distinct emails classified `other_user` by `classifyActor` (reuse the one in `lib/jarvis/tools/get-change-history.ts`; export it if needed but do not change its behavior).
- hours: `segments.hour, metrics.cost_micros, metrics.clicks, metrics.conversions, metrics.phone_calls` FROM campaign, LAST_30_DAYS, enabled campaigns; summed per hour, 24 rows.
- products: `segments.product_item_id, segments.product_title, metrics.cost_micros, metrics.conversions, metrics.conversions_value` FROM shopping_performance_view, LAST_30_DAYS, ORDER BY cost DESC, LIMIT 50.
Money is micros / 1,000,000 rounded to 2 decimals. No customer data in logs (log only signal key and error code).

`saveSignals` inserts one `job_runs` row: `job_name = signalsJobName(accountId)`, status `success` (all ok) or `partial`, `details = { signals }`, `finished_at`, `processed` = number of ok signals, `error_count`. `loadStoredSignals` returns the newest row's `details.signals` when `version === 1` and `readAt` is within `SIGNALS_TTL_HOURS`. Both never throw.

`POST /api/setup/signals`: same-origin check, signed-in user, `isAdaptiveOnboarding(process.env, user.email)` else 404, rate limit (scope `setup_signals`, 10 per 10 minutes per user), resolves the business's selected linked account through the user's RLS client (pattern: `app/api/setup/answer/route.ts` and `lib/jarvis/turn.ts`, select `id, customer_id, manager_id, currency_code, refresh_token_encrypted`), returns `{ ok: true, fresh: false }` when a stored read is fresh, else decrypts the token, builds the client with `getCustomer`, reads with `connectedEmail = user.email` and `ownManagerIds = ['7561141000', ...getConfiguredGoogleAdsManagerIds()]`, saves with the admin client, returns `{ ok: true, fresh: true, okSignals: n }`. No subscription gate: it costs no AI.

Operator page `/operations/onboarding-signals` (use `requireOperatorPage` and the look of `app/(dashboard)/operations/ops-ui.tsx`): lists the operator's own linked accounts only, a «اقرأ الحساب» button per account posting to `POST /api/operations/onboarding-signals { accountId }` (operator check like the other `/api/operations/*` routes, and the account must belong to the operator's own business). It runs a fresh read (ignores the TTL), saves it, and returns the signals plus `classifyScenario(...)`. The page shows every signal as read or failed with its error code and a compact value, then the scenario. This page is how Ayman checks fields on real accounts before any branch opens.

Tests (`tests/adaptive-signals.test.ts`, node:test like the other tests): a fake `GaqlCustomer` that answers by the FROM resource; every signal's mapping; one failing query leaves the others ok; the deadline turns a hanging query into `{ ok:false, error:'timeout' }`; store round trip with a fake admin client; TTL.

## Part B: engine
Implement the stubs exactly as their doc comments say, following design sections 2 to 4. Specifics:

**classifyScenario.** State order: `connectNoAccount` or `answered.has_account === 'none'` with no linked account gives no_account; then from `signals.campaigns` (when ok): no non-removed campaigns or (30-day cost 0 and impressions 0) gives new, or dormant when paused campaigns exist; then cost > 0 and `enabledConversionActions` ok and 0 gives no_tracking; then cost > 0, actions > 0, conversions 0 and clicks >= `TRACKING_SUSPECT_MIN_CLICKS` gives tracking_suspect; else active. With `signals` null or campaigns failed and an account linked, state is active and kindConfidence none (we ask everything). managed: `answered.manager` agency or employee gives confirmed; else externalManager.linked or otherEditors14d >= 1 gives suspected. Kind scores (design section 2 table): host contains salla.sa, salla.store, zid.store or myshopify.com +3 for ecommerce and sets platform; merchantCenterLinked +3; SHOPPING or PMAX with purchase conversions +2; value30 > 0 +1; clinic words in campaign names +3 (Arabic and English, e.g. أسنان، تقويم، زراعة، عيادة، مجمع طبي، جلدية، ليزر، علاج طبيعي، عيون، dental, clinic, derma); call or booking the largest conversion group +1 for clinic and services; services words +3 (مقاولات، ترميم، صيانة، تنظيف، نقل عفش، مكافحة حشرات، مظلات، عزل، سباكة، تكييف، ديكور، شركة); LOCAL campaign or locations > 0 +2 for local; directions or store_visit +2 for local; restaurant words +3 (مطعم، كافيه، قهوة، فرع، مشويات، حلويات، restaurant, cafe). Confident when top >= 3 and leads the second by >= 2; guess when top >= 1; else none. A stated type (`answered.type`, mapped from `TYPE_OPTIONS` ids: ecommerce to ecommerce, clinic to clinic, services and real_estate to services, restaurant and local_store to local, education and other to general) overrides with kindConfidence stated. A `confirm` of `no` drops confidence to none. specialty from clinic words (dental, derma, else general). outcome from the largest conversion group (purchase to purchases, call to calls, lead_form or contact to forms, booking to bookings, directions or store_visit to visits). evidence: short codes like `host:salla`, `mc`, `words:clinic`, `conv:call`.

**adaptivePending.** Per design section 3. With an opener proposal (kindConfidence confident and state active, no_tracking, tracking_suspect) the first key is `confirm` unless answered. `confirm = no` adds `type` and `goal` back. Never ask a key already in `answered`, except in edit mode where every scenario key except confirm and has_account is asked with its current choice marked. `consent` only when hasAccount and managed is not confirmed. `manager` is asked (first after confirm) when managed is suspected, and skipped when none and the account answers it (keep it when there is no read). new, dormant and no_account: type, focus_service, regions, goal, budget, website. Each kind's list is in section 3; general uses the legacy ten minus what the account answers. no_tracking and tracking_suspect add `tracking_now` after the kind's list, before budget.

**adaptiveQuestion.** Copy and options per key and kind. Legacy keys get kind wording only where the design says (value for clinic «كم يدفع المريض تقريباً في أول زيارة؟», pain and goal per kind with new ids); everything else returns null so the legacy dock is used. Options for focus_service come from a per-specialty or per-kind catalog plus campaign names that match it. push_products options are the top 6 product titles by cost when `signals.products` is ok (ids `p_<index>`; the label is the title, cleaned with `cleanUserText`), else free text. call_hours options carry explicit windows in their labels and ids (for example `split_9_13_16_22` «فترتين: 9 الصبح لين 1، و4 العصر لين 10 الليل», `day_8_23`, `evening_16_24`, `always`). aov_check exists only when value30 and conversions30 give an average; its text states it («متوسط طلبك من قوقل طلع قرابة 186 ريال. قريب من الصح؟»).

**answers.ts.** One catalog per key holding every scenario's ids; `parseAdaptiveAnswer` accepts only catalog ids (push_products accepts `p_0` to `p_9` plus cleaned free text up to 120 chars; focus_service accepts `other` with text 2 to 40 chars). Effects write only `sector` and `primary_goal` (from confirm yes) and one fact per answer with `data.setup_key` and `data.choice` (and `choices`/`text` when present), kinds from the memory table's list.

**opener, understanding, decisions, endings.** As in design sections 3 and 4 and the snapshots: the opener only states what was read (two to four `seen` rows), the headline names kind, city and outcome only when each was read, and `ask` is «صح كذا؟» or a variant. understandingRows lists activity, what they want, value or average order, margin, push products, call hours, pain, budget, each with its source. scenarioDecision: call_hours when hours ok and the answer has windows and cost outside the windows is >= max(100, 10% of 30-day cost) or phone calls outside >= 5 (title «وقّف الإعلان من X لين Y» naming the largest closed stretch, reason with the cost and calls, why from the answer, steps for setting an ad schedule in Google Ads); idle_products when products ok and products with cost30 >= 50 and conversions30 = 0 total >= 200 (title «أوقف N منتجات تصرف وما تبيع», why quoting margin when answered); tracking_setup first for no_tracking and tracking_suspect with steps per kind and platform (Salla, Zid and Shopify have their own Google integration paths; say «من لوحة سلة» level only, no invented menu paths). planReason gives one honest line from focus_service and pain, or null. firstCampaignPlan: per kind a campaign type (search for clinic and services; PMax with a feed when merchantCenterLinked else search for ecommerce; search plus location assets for local), regions and budget from answers, three to five items mixing structure, first keywords from focus_service labels, tracking, and a budget line; next is open_account for no_account else trial. agencyQuestions: one plain question per audit decision category present (bidding, keywords, ads, structure, budget, targeting, extensions), at most five.

Tests (`tests/adaptive-engine.test.ts`): every state and kind branch, confidence thresholds, stated override, confirm no, pending lists for the two snapshot scenarios (clinic active: confirm, focus_service, value, profit_per_deal, close_rate, pain, call_hours, whatsapp_booking, budget, consent; ecommerce on Salla: confirm, aov_check, margin, push_products, exclude_products, pain, budget, consent), edit mode, parse accept and reject cases, effects, opener with failed signals, both decisions on and below their thresholds, firstCampaignPlan for each kind, and a copy check that no returned Arabic string contains U+2014 or U+2013.

### C1: server state
1. **`lib/setup/adaptive/view.ts` (new): `buildAdaptiveView(input)`**, pure and synchronous, unit tested. Input: the signals (or null), linked account count, whether an account is chosen, the connect job error code, ledger choices and labels, business (`name, monthlyBudget, targetRegions, website`), `consentAnswered`, `edit`, `firstName`, the audit row presence, `subscriptionActive`, the `Plan` (or null) and the plan decisions' categories. Output: `{ view: AdaptiveView, pending: SetupKey[], stage: SetupStage, plan: Plan | null }`. Rules:
   - `scenario = classifyScenario({ signals, linkedAccounts, connectNoAccount, answered })` where `connectNoAccount` is the connect job error `no_accounts` or `no_client_accounts`.
   - **pending**: with a linked and chosen account, `adaptivePending({ scenario, answered, consentAnswered, edit, hasAccount: true })`. With no linked account, questions run only after the customer chose to go on without one: ledger `has_account === 'none'` gives `adaptivePending({ ..., hasAccount: false })`; otherwise `[]`.
   - **stage**: start from `resolveSetupStage` exactly as today, then override only here: no linked account and `has_account === 'none'` gives `questions` while pending, else `finishing` (never `done`: there is no home without an account). new or dormant with nothing pending gives `finishing`, or `done` when `subscriptionActive`. A connect job that is running still wins (`connecting`).
   - **needsRead**: account linked and chosen, not edit, and `!canReuseStoredSignals(signals)`.
   - **opener**: `buildOpener(scenario, signals, { firstName })` only when not edit and `confirm` is pending; else null.
   - **questions**: for every pending key, `adaptiveQuestion(key, { scenario, signals, answered, edit })`; keep the non-null ones.
   - **understood**: `understandingRows(...)` when nothing is pending and not edit; else `[]`.
   - **ending**: `first_campaign` for new, dormant, no_account; else `agency` when `managed === 'confirmed'`; else `tracking` for no_tracking and tracking_suspect; else `plan`.
   - **auditAllowed**: state is active, no_tracking or tracking_suspect.
   - **decision**: `scenarioDecision({ scenario, signals, answered, currency })`. When it is non-null and a plan exists, return a plan where `first` is null, the old first is prepended to `locked` as `{ id, title, severity }` only (its reason and amounts never reach the browser), and `decisionsCount` is unchanged. Put this as a pure helper `withScenarioLead(plan)` in `lib/plan/plan.ts` with tests. The one-open-decision lock (#101) stays: the rules decision takes the open slot.
   - **no waste for no tracking**: for no_tracking and tracking_suspect the returned plan has `waste: null` (the number is never sent).
   - **firstWhy**: `planReason({ scenario, answered, labels, decision: { title: plan.first.title, category } })` when there is no rules decision and `plan.first` exists; else null.
   - **firstCampaign**: `firstCampaignPlan(...)`. **agencyQuestions**: `agencyQuestions(decisions with categories)` only for the agency ending. **fullManagementCard**: `AGENCY_FULL_MANAGEMENT_CARD` and ending agency.

### C2: screen
Work in `app/onboarding/setup/` (split new UI into new files there, e.g. `adaptive-docks.tsx`, `adaptive-cards.tsx`, to keep `setup-chat.tsx` readable). Everything new runs only when `state.adaptive` is non-null.

Only once per page load (a ref): if the post fails or times out, continue with the state as it is (the tree then asks more). Never show an error for it.
2. **Opener** (when `adaptive.opener` is non-null at the start of questions, not edit): a greeting line, then a «اللي شفته» box listing `seen` (small, muted, one row each), then `headline` as the big line and `ask` under it, then a confirm dock with two tiles from `CONFIRM_OPTIONS` (yes first). 3. **Questions**: for each pending key, if `adaptive.questions[key]` exists use its `text` (big) and `why` (note), and render an `AdaptiveDock`: `tiles` one per row (reuse `AnswerTile`), `tiles2` a two-column grid, `chips` multi-select pills with a «تم» button (push_products, peak_hours); `freeText` shows an input with its placeholder and maxLength next to the options (focus_service sends `{ choice: 'other', text }`, push_products sends `{ choices, text }`, exclude_products sends `{ choice: 'text', text }`); a question whose `options` is empty shows only the input. In edit mode the `current` option is marked like the legacy docks do. A pending key with no adaptive question uses the legacy `questionCopy` and `QuestionDock` unchanged. The customer's bubble is the server's `label` from the answer response when present, else the tapped label.
4. **Re-plan after keys that change the tree**: after answering `confirm`, `type`, `manager` or `has_account`, `reload()` and replace the remaining queue with the new `pending` (and its count).
5. **The free audit**: in the adaptive path start it only when `adaptive.auditAllowed`, not edit, no audit on record, and neither `type` nor `confirm` is pending (at the start of questions, or right after `type`/`confirm` is answered and the reload shows them gone). For new, dormant and no_account never call `/api/audit/run`.
6. **«فهمت عليك»**: when questions finish (not edit), `reload()`, then show a card titled «فهمت عليك» listing `adaptive.understood` rows (label, value, and a small source tag: account «من حسابك», confirmed «أكدته»، you «قلته»), with «صح، وريني الخطة» (primary) and «عدّل شي» (link to `/onboarding?edit=1`). Only after «صح» does the ending show. If the audit is still running at that point, the existing waiting flow takes over before the plan.
7. **Endings**:
   - `plan` and `tracking`: the existing «خطتك جاهزة» `PlanCard`. Add optional props to `PlanCard` (`lead?: ScenarioDecision`, `firstWhy?: string | null`): with `lead`, the open block shows its `title`, `reason`, a «ليش أول شي» line with `why`, and its `steps` as a short numbered list (no «اعتمد»: these are manual), in place of the audit's first decision; without `lead` and with `firstWhy`, a «ليش أول شي» line under the audit's first decision. Locked rows and CTA unchanged. `/home` and `PlanLock` pass neither prop and must render exactly as today.
