## 1. Flags off: no behaviour change

All of the checks below were confirmed by reading the code.

- **Crons.** `/api/cron/guard`, `/api/cron/measurement` and `/api/cron/monthly-review` check auth and then the flag before they create a client or touch a table. With the flag off each answers 200 `{"skipped":"disabled"}`. Missing tables are never reached. The workflow accepts 200/404/409 for measurement and 200/409 for guard, and monthly uses `--fail-with-body` against a 200, so no job fails. One cost: the guard job adds two runner starts a day and monthly adds three a month. That is negligible.
- **The optimize cron with flags off** does none of the new work: the shadow and autonomy loaders are `null` (no read), `prepareOptimizerLoops` returns `EMPTY_LOOPS_CONTEXT` with no I/O, `applyLoopFilters` returns the same array, `loopsPromptAddendum` returns `''` (the prompt is byte-identical), `ad_assets` is not set, the handoff refresh is skipped, the ads-studio queue is skipped and `withBaseline=false` keeps the old impact queries. The one new runtime cost on every call is `checkGuardrails`, which calls `isShadowAccount`. With the flag off that returns `false` before it reads anything.
- **Jarvis.** The tool lists are built at module load from the flags, so with flags off the list is the same as on main. `prepare_change` returns the same tool object (`PREPARE_CHANGE_TOOL`), `save_merchant_context` is not offered, and `guardCardLines` returns `[]` with no read.
- **UI.** `/home` (guard alerts behind `isGuardEnabledForUser`), the nav (`showLeads` is false), the operations tabs, the handoff card, the autopilot level picker and `/optimizer` (only new preview branches for operations that cannot exist with flags off) are all unchanged.
- **Middleware and robots.** Both gain `/leads`, a page that 404s while the flag is off. It is harmless and correct.
- **Executable boundary.** `buildExecutableAction` returns `null` for extended, launch and measurement operations while their flags are off. The allow-list only grows under `isLeadLoopServing()`.
- **I-1 (Info).** `.github/workflows/scheduled-jobs.yml:57`: the comment said the route answers 404 with the flag off, but it answers 200 skipped. **Fixed** (comment only).

## 2. Money safety

### H1. Autonomy level `small_and_notify` executes negatives that the older gate refused (High). **Fixed**
`lib/autopilot/autonomy.ts` (`evaluateAutonomy` and `smallRule`, around lines 222 and 306). With the level on, `applyAutonomyLevel` replaces the conservative verdict with `evaluateAutonomy`. That function dropped three checks from `evaluateAutopilotPolicy`: `relevance === 'clearly_irrelevant'`, `window_days >= 14` and `clicks >= 8`. It also dropped `settings.allowed_actions`. The migration backfills `small_and_notify` for every account already in conservative mode. Turning the flag on would therefore auto-add exact negatives the model marked `uncertain`, or ones based on 7 days or 2 clicks, on accounts whose owners never chose the new level. Those owners only opted into the stricter V1 rule. The change looks small, but a wrong negative blocks a converting search, and the change runs with nobody approving it.
Fix: the small-level negative rule now also requires the V1 evidence (14 days, 8 clicks, clearly irrelevant), and the merchant's `allowed_actions` list is honoured. Tests added in `tests/trust-autonomy.test.ts` (2).

### M1. Monthly Opus cost cap priced at the preferred model only (Medium). **Fixed**
`lib/loops/monthly-run.ts:284`. `withinCostCap` priced the worst case at `getModelForAgent('jarvis_deep')`. But `createMessageForAgent` walks a candidate list, and for the opus tier that list includes `claude-opus-4-1-20250805` at $15/$75. That is about 3.75x the opus-5-5 rate. If the preferred id is unavailable, the real call can cost several times the "hard" cap. The cap is now checked against the priciest candidate (`priciestModel`). Test added in `tests/loops-monthly.test.ts`.
Residual (Info I-2): there is no run-level USD ceiling. The total is bounded by `MAX_ACCOUNTS` (25) × `MAX_COST_USD` ($0.5) for each invocation, and the run executes on 3 days, so the worst case is about $37 a month at the defaults. That is acceptable, but it should be written down.

### M2. Undo stranded when a flag goes off (Medium). **Fixed**
`lib/ai/optimizer-agent.ts:1099` and `lib/ai/extended-actions/execute.ts:356`. `executeRollback` threw "Extended actions are disabled" for `ext_*` rollbacks when `EXTENDED_ACTIONS_ENABLED` was off, and the ads-studio rollback threw likewise when `ADS_STUDIO_ENABLED` was off. Turning a flag off to stop new changes would then trap the merchant's 30-day undo of changes that were already applied. That runs against the rollback route's own rule ("a compensating safety operation… must remain available"). The rollback still passes `rollbackResourcesScoped`, a validateOnly call and the claim. The existing test was updated to the new contract.

### M3. Shadow loader in the optimizer failed open (Medium). **Fixed**
`lib/shadow/guard.ts:49`. `loadShadowAccountIds` returned an empty set on any non-missing-table error. In that case a shadow account was treated as a normal one, so its cards were queued to the merchant-facing approval centre, its handoff was refreshed, and with autonomy on it could execute. That last path is still blocked by `checkGuardrails`, which fails closed, but the queueing was not. `excludeShadowAccounts` and `isShadowAccount` both fail closed, so this one was inconsistent. It now holds every account back for that run: decisions are only recorded as shadow. Test added.

### Checked and fine
- **No path raises total spend or enables a campaign without a card.** Launch builds PAUSED (`lib/launch/operations.ts:86`) and the enable step is a separate `enable_campaign` card (`lib/launch/recommendation.ts`). Autonomy cannot execute `adjust_budget`, `enable_campaign` or targets (`NEVER_AUTOMATIC_TYPES` plus the `AUTONOMY_SMALL_ACTIONS` allow-list), and `executor.ts` re-checks the type. `evaluateBudgetShift` is exact in micros, though nothing calls it yet (I-3). Network settings can only be turned off. Bid modifiers stay inside 0.5 to 1.5.
- **Google recommendations.** Only `SITELINK_ASSET`/`CALLOUT_ASSET` can be applied. The type is re-read at preflight. Budget, target and bidding types are triage only. There is no validateOnly, so a fresh read stands in for it, and apply is marked not reversible on the card (`preflight.ts:506`).
- **Rollback descriptors** capture old values before the mutate: modifiers (`restore_modifiers`), primary flags (`restore_conversion_primary`, items built from the read), and launch (`executeLaunchRollback` refuses while the campaign is ENABLED and is scoped to one customer). `rollbackResourcesScoped` checks every `ext_*` list.
- **validateOnly before live**: the approval handler (`action-handler.ts:405`), the autopilot executor and the rollback route all do it. Launch has its own `validateLaunchOnly`.
- **Offline uploads are idempotent**: the claim is a single SQL statement with `FOR SKIP LOCKED`, `order_id` is the lead id, DUPLICATE_ORDER_ID counts as done, and an empty result is a retry, never success. Transport `maxAttempts: 1`.
- **Shadow accounts are never executable**: `checkGuardrails` checks shadow first, the `shadow_decisions.executable` CHECK makes `executable = true` impossible, decisions are not in `recommendations`, and guard, monthly, upload and scan all skip shadow accounts.

### M4. `/w/[slug]` lets anyone mint lead rows that can be uploaded as conversions (Medium, open, decide before enabling LEAD_LOOP)
`lib/lead-loop/redirect-handler.ts:82`. The link is public by design, so anyone can append a syntactically valid but fake `gclid` and create a lead row. That does not reach Google by itself: the merchant has to mark the row "صار زبون", and Google rejects unknown gclids (EVENT_NOT_FOUND counts as permanent). So the money risk is low, but the inbox can be flooded. The limits are 20 a minute per IP per slug and 600 an hour per slug. The bot filter only matches UA patterns. Suggest showing "has click id" only for gclids seen in `click_view` before an upload, or at least labelling unverified clicks in the inbox. Not changed here because it is a product call.

## 3. Security

- **`/w/[slug]`: no open redirect.** The target is always `https://wa.me/<digits>`, the number is normalised and the DB CHECK enforces `^[1-9][0-9]{7,14}$`. The text is `encodeURIComponent` of cleaned merchant text (bidi and control characters stripped, 300 chars). Visitor input never reaches the URL: the ref code is server generated. No IP, UA or phone is stored. Responses are `no-store`, `noindex` and `no-referrer`. The slug is validated before any read. **I-4:** the 404 vs 302 difference lets a caller test whether a slug exists, but slugs are 8 to 16 chars from a 31-char alphabet, so this is acceptable.
- **Landing-check SSRF guard.** Https only, port 443, no credentials, no IP literals in any spelling (the URL parser normalises 0x7f.1 and the like). Every hop runs `parseCheckableUrl` plus `resolvePublicAddresses`, with a cap of 3 redirects. IPv6 checks cover ::1, mapped and compatible addresses, NAT64, 6to4, Teredo, ULA, link-local and multicast, and only 2000::/3 is allowed. All answers are judged and any private answer rejects the whole set. The connection is pinned to the checked address through the `lookup` override, and SNI/Host keep the real name. Body is capped at 1.5 MB, total time at 5 s, and no cookies are sent. I see no rebinding window. **L3 (Low, open):** a `Location` to a non-https scheme is refused (good). Redirects are followed for `GET` only, which is good too. Nothing to change.
- **New API routes.** Same-origin checks, auth and a rate limit everywhere. Account ownership goes through `getLinkedGoogleAdsAccount` (leads settings and mark, handoff request, launch propose, autopilot level). Operator routes use `isOperatorUser`, answer 404 otherwise, and are flag-gated. `markLead` scopes by `account_id` from the verified account. The launch draft is scoped by `user_id` and `account_id`.
- **M5 (Medium). Lead-loop "operators" mode leaked into everyone's account (Fixed).**
  - `lib/jarvis/tools/get-conversion-health.ts:317` checked `isLeadLoopEnabled(env, ctx.connectedEmail)`, but `turn.ts` never set `connectedEmail`, so in "operators" mode the measurement block never appeared for allowed users. It now uses the owner's email (`ownerEmail`, set in `turn.ts:149`).
  - More important: `app/api/cron/measurement/route.ts:115` scanned **every** billable account in "operators" mode, and the scan writes data-exclusion and lead-action cards into ordinary merchants' approval centres. Once approved, those become live mutates, because `buildExecutableAction` allows them under `isLeadLoopServing()`. In "operators" mode the scan is now limited to accounts whose owner passes `isLeadLoopEnabled`, and it fails closed if the owner lookup fails.
- **RLS in the 7 migrations.** All of them enable RLS. Owner tables get SELECT only, scoped through `businesses.user_id = auth.uid()`. Writes come from the service role only, and the shadow tables have no grant at all. `claim_lead_uploads` is SECURITY DEFINER with a pinned `search_path`, and EXECUTE is granted to service_role only. **L4 (Low, open):** `merchant_context_owner_read` has no `TO authenticated` and uses bare `auth.uid()`, not `(select auth.uid())`. Access is the same because of the grants, but it is not consistent with the others and is slower per row.
- **L5 (Low, open).** `app/api/operations/shadow/route.ts:49` marks a shadow account by `customer_id` and refuses an ambiguous match (good). It does not refuse `is_manager` rows. That is harmless, but worth a guard.

## 4. Correctness

- **Arabic copy.** No em or en dash in any added user-facing Arabic string (checked by script over the added lines). Writers and validators reject dashes. **L6 (Low, open):** `lib/guard/copy.ts:15` `cleanName` turns a merchant's long dash into ` - `, which is not a dash ban violation but is a Latin hyphen inside Arabic sentences. The rest of the code turns it into `،`. Consider making it consistent.
- **Guard dedupe.** One row per `(account_id, dedupe_key)` with a unique constraint, plus reopen and resolve only when the source was readable, and one mail per owner per Riyadh day. **L7 (Low, open):** the `outside_change` key hashes the exact set of changes seen in the 24-hour lookback (`detectors.ts:575`). Because the 18-hour recheck runs inside that window, the same batch read on consecutive days can form a different set and therefore a new key, which means a second mail about the same edit. Its severity is medium or info, and info is never mailed. Keying on the newest change (or on each change) would fix it.
- **Monthly report.** It is written once per (account, month) through the existing unique index. `reports.period_type` already allows `monthly`. Both mail copies (`monthly_report`, `guard_alert`) ship `approved: false`, so nothing is sent until Ayman approves them.
- **L2 (Low). Fixed.** `get_landing_check` and `get_response_coaching` did not re-check their flag at run time. The loop tools do, and the tool list is fixed at start-up, so a flag turned off without a restart would still let these run. They now check it, with an injectable flag for the tests. Test added.
- **I-5.** The `TOOLS_BY_NAME` map always contains the five optional tools. That is harmless, because a name is only dispatched if it appears in `JARVIS_READ_TOOLS` (`brain.ts`), and the loop tools check their flag again.
- **I-6.** An agency shadow account still pays the hourly Sonnet optimizer call. This is by design, but it should be counted in the cost dashboard.

## Decisions for Ayman before turning flags on
1. **L1. Autonomy backfill.** `20261020_trust_autonomy_levels.sql:36` moves every account in conservative mode to `small_and_notify`, which now also allows **keyword pauses** with no approval. Pauses are new behaviour that those owners never agreed to. Even with H1 fixed, I would drop the backfill (or backfill only for opted-in operators) and let merchants choose the level.
2. **M4.** Decide how the inbox treats lead clicks that carry an unverified click id.
